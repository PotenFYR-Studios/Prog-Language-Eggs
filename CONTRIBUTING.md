# Contributing to Prog-Language-Eggs

Thanks for helping make the one-egg-for-every-language runtime better! This
document explains what contributions look like here and how changes are
validated.

## Ground rules

- **The egg JSON is generated by the panel**: `egg-programming-multi.json`
  carries a `DO NOT EDIT` header. Structural edits (variables, images,
  scripts) are made through the panel export flow and re-exported; if you
  hand-edit, keep the PTDL_v2 shape byte-faithful (see below) and say so in
  your PR.
- **No invented languages.** The 54-language matrix in the README and the
  docs site is generated from real launcher code (`run.sh`,
  `install-runtime.sh`, `resolve-version.sh`). A new language needs:
  1. a real runner resolution path in the launcher,
  2. real auto-detect file triggers,
  3. a checksum-verified upstream source in `resolve-version.sh` /
     `install-runtime.sh`.
- **Branch**: `master` is the integration branch. Fork + feature branch, PR
  against `master`.
- **Keep the launcher POSIX-bash clean**: `run.sh` and friends must keep
  working under `ash`-based install containers and busybox constraints where
  the install script runs.

## Egg JSON expectations

Any change to `egg-programming-multi.json` must preserve:

- `meta.version: PTDL_v2` and `meta.update_url` pointing at the raw file on
  the default branch (this is what the launcher's `EGG_UPDATE_URL`
  self-update checks).
- Variable objects with all eight PTDL_v2 fields: `name`, `description`,
  `env_variable`, `default_value`, `user_viewable`, `user_editable`,
  `rules`, `field_type`.
- Laravel-style validation `rules` on every user-facing variable, and
  `user_editable: false` for panel-managed values like `SERVER_PORT`.
- The `file_denylist` entries protecting launcher scripts
  (`run.sh`, `entrypoint.sh`, `install*.sh`, `resolve-version.sh`,
  `.potenfyr`).
- The startup command (`bash /usr/local/bin/run.sh`) and stop signal
  (`^C`) semantics.

## Validation (run before pushing)

```bash
# Behavior suite: boots the launcher in a docker mirror of the real image
# and drives panel lifecycle events (start/stop/kill/restart, console-text
# stop, crash diagnostics, multi-process sweep, multi-port apps, pinning).
bash tests/panel-test.sh

# Sync rules (git clone/fetch-over-workspace behavior)
bash tests/sync-test.sh

# Console rendering / banner checks
bash tests/render-test.sh
```

CI runs the behavior suite on every PR and blocks publish on failure
(`.github/workflows/docker-image.yml`).

## Docs changes

The documentation site lives in `docs/` (Vite + React + Tailwind v4, built
with Bun). Its content is **generated from the real repo data at build
time** (`docs/scripts/prebuild.ts` reads `egg-programming-multi.json` and
the README language matrix into `catalog.json`), so never hardcode a
language, image or variable value into page copy. Use the
`eggVar("VARIABLE_NAME")` helper when referencing an egg variable.

```bash
cd docs
bun install
bun run dev     # local preview on :5184
bun run build   # production build into docs/dist
```

## Pull requests

- Use the PR template; link the issue you're fixing.
- Keep PRs focused: one behavior change per PR.
- New variables need: egg JSON entry, launcher handling, README variable
  table row, and a docs mention (which the generator picks up
  automatically once the JSON lands).
- Commits follow Conventional Commits (`feat:`, `fix:`, `docs:`, `ci:`,
  `chore:`).
